En un primer ejercicio de Machine Learning es normal escribir todo en un único notebook:

cargar datos → explorar → transformar → entrenar → evaluar

Esto funciona para aprender un algoritmo, pero empieza a producir problemas cuando queremos que el experimento sea reproducible, que otras personas puedan entenderlo o que el modelo pueda utilizarse fuera del notebook.

En esta guía organizaremos el proyecto como una secuencia de etapas conectadas. Cada notebook tendrá una responsabilidad clara y producirá artefactos que serán consumidos por la siguiente etapa.

1. El flujo completo

flowchart TD
    A[Datos originales] --> B[Profiling y split]
    B --> C[Train y test]
    C --> D[EDA sobre train]
    C --> E[Pipeline de procesamiento]
    D --> E
    E --> F[Entrenamiento y validación]
    F --> G[Modelo campeón]
    G --> H[Evaluación final en test]
    G --> I[Inferencia]
    H --> J[Métricas finales]
    I --> K[Predicciones]

La idea principal es sencilla:

Cada etapa recibe entradas bien definidas, realiza una responsabilidad y produce salidas verificables.

2. ¿Por qué dividir los notebooks?

2.1. Separación de responsabilidades

Un notebook que carga datos, entrena diez modelos, modifica variables y evalúa test repetidamente es difícil de entender. Al dividirlo, cada archivo responde una pregunta concreta:

Etapa Pregunta principal
Datos ¿Los datos son válidos y cómo deben dividirse?
EDA ¿Qué podemos aprender del conjunto de entrenamiento?
Procesamiento ¿Cómo se convertirán los datos originales en entradas para el modelo?
Entrenamiento ¿Qué modelo e hiperparámetros funcionan mejor?
Evaluación ¿Cómo generaliza el modelo elegido a datos no observados?
Inferencia ¿Cómo usamos el modelo con observaciones nuevas?

2.2. Protección del conjunto de prueba

El conjunto de test simula datos futuros. Si lo usamos para seleccionar variables, escoger modelos o ajustar hiperparámetros, deja de ser una evaluación independiente.

Por eso:

  • train se usa para explorar, diseñar y entrenar;
  • la validación cruzada sobre train se usa para seleccionar modelos;
  • test se utiliza una sola vez, después de elegir el modelo campeón.

2.3. Reproducibilidad

La división permite ejecutar nuevamente una etapa sin rehacer todo el proyecto. También hace visibles las decisiones:

  • semilla aleatoria;
  • porcentaje del split;
  • columnas utilizadas;
  • transformaciones;
  • métrica de selección;
  • hiperparámetros finales.

2.4. Depuración

Si algo falla, sabemos en qué etapa buscar:

  • columnas incorrectas: pipeline de datos;
  • fuga de información: procesamiento o entrenamiento;
  • modelo que no carga: persistencia;
  • predicción con columnas desordenadas: contrato de inferencia.

2.5. Transición hacia MLOps

Los notebooks siguen siendo herramientas de aprendizaje y experimentación. Sin embargo, esta organización se parece a un sistema real:

pipeline de datos → pipeline de entrenamiento → pipeline de inferencia

Más adelante, el código estable puede moverse de los notebooks a funciones y scripts automatizados.

4. Notebook 1: profiling y separación de datos

Objetivo

Cargar la fuente original, revisar su calidad y crear una división reproducible entre entrenamiento y prueba.

Carga desde CSV

from pathlib import Path
import pandas as pd

PROJECT_DIR = Path.cwd()
DATA_PATH = PROJECT_DIR / "data" / "raw" / "breast_cancer.csv"

df = pd.read_csv(DATA_PATH)

Path.cwd() devuelve el directorio de trabajo actual. No necesariamente es la carpeta donde está guardado el notebook; es la carpeta desde la que se inició Jupyter.

Si los notebooks están dentro de notebooks/, podemos normalizar la ruta:

PROJECT_DIR = Path.cwd()

if PROJECT_DIR.name == "notebooks":
    PROJECT_DIR = PROJECT_DIR.parent

Profiling básico

Antes de modelar revisamos:

print("Forma:", df.shape)
print("Duplicados:", df.duplicated().sum())
print("Valores faltantes:", df.isna().sum().sum())
print("Tipos de datos:")
print(df.dtypes)
print("Distribución de clases:")
print(df["target"].value_counts())

El profiling no es todavía un análisis profundo. Es una verificación inicial de que la fuente puede procesarse.

Split

from sklearn.model_selection import train_test_split

train_df, test_df = train_test_split(
    df,
    test_size=0.20,
    stratify=df["target"],
    random_state=42,
)

¿Por qué stratify?

Mantiene aproximadamente la misma proporción de clases en train y test.

¿Por qué random_state?

Permite repetir exactamente la misma partición. Sin una semilla, dos ejecuciones pueden producir conjuntos diferentes y métricas distintas.

Salidas

train_df.to_csv("data/processed/train.csv", index=False)
test_df.to_csv("data/processed/test.csv", index=False)

También guardamos un contrato:

contract = {
    "target": "target",
    "features": df.drop(columns="target").columns.tolist(),
    "random_state": 42,
    "test_size": 0.20,
    "target_names": ["malignant", "benign"],
}

El contrato documenta el esquema que las etapas posteriores deben respetar.

5. Notebook 2: análisis exploratorio de datos

Regla principal

El EDA se realiza únicamente sobre entrenamiento.

train_df = pd.read_csv("data/processed/train.csv")

X_train = train_df.drop(columns="target")
y_train = train_df["target"]

Qué buscamos

  • distribución de clases;
  • escalas y distribuciones de las variables;
  • valores extremos;
  • correlaciones;
  • relaciones potenciales con la variable objetivo.

Ejemplo:

import matplotlib.pyplot as plt

y_train.value_counts().sort_index().plot.bar()
plt.title("Distribución de clases en entrenamiento")
plt.xlabel("Clase")
plt.ylabel("Número de observaciones")
plt.show()

Correlación con la variable objetivo:

correlations = (
    train_df.corr(numeric_only=True)["target"]
    .drop("target")
    .abs()
    .sort_values(ascending=False)
)

correlations.head(10)

El EDA debe producir decisiones

Una gráfica no es el resultado final del EDA. Debemos convertir observaciones en decisiones:

Hallazgo Decisión posible
Escalas muy diferentes Estandarizar para KNN y regresión logística
Valores faltantes Incorporar imputación al pipeline
Clases desbalanceadas Usar split estratificado y métricas apropiadas
Variables correlacionadas Ser cautelosos al interpretar coeficientes

6. Notebook 3: procesamiento y feature engineering

Transformaciones reproducibles

El procesamiento no debe consistir en modificar manualmente el DataFrame y olvidar cómo se hizo. Debe representarse mediante objetos reproducibles.

from sklearn.impute import SimpleImputer
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler

numeric_scaled = Pipeline([
    ("imputer", SimpleImputer(strategy="median")),
    ("scaler", StandardScaler()),
])

Para un árbol no necesitamos estandarización:

numeric_tree = Pipeline([
    ("imputer", SimpleImputer(strategy="median")),
])

ColumnTransformer

ColumnTransformer permite aplicar transformaciones distintas según el tipo de variable:

from sklearn.compose import ColumnTransformer

scaled_preprocessor = ColumnTransformer([
    ("numeric", numeric_scaled, feature_columns),
])

Aunque el dataset actual solo tenga variables numéricas, esta estructura puede extenderse a variables categóricas.

¿Por qué no ejecutar fit_transform todavía?

El preprocesador aprende información de los datos:

  • la mediana para imputar;
  • la media y desviación para estandarizar;
  • categorías conocidas en un encoder.

Si ajustamos esas transformaciones antes de la validación cruzada, cada fold recibe información de los otros folds. Esto es data leakage.

7. Notebook 4: entrenamiento y selección

El pipeline completo

El modelo debe contener procesamiento y estimador:

from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline

logistic_pipeline = Pipeline([
    ("preprocessing", scaled_preprocessor),
    ("classifier", LogisticRegression(max_iter=5000)),
])

Cuando ejecutamos:

logistic_pipeline.fit(X_train, y_train)

ocurren dos cosas:

  1. el preprocesador aprende sus parámetros usando X_train;
  2. el clasificador se entrena con los datos transformados.

Durante predict, el mismo objeto aplica exactamente las mismas transformaciones.

Validación cruzada

from sklearn.model_selection import StratifiedKFold

cv = StratifiedKFold(
    n_splits=5,
    shuffle=True,
    random_state=42,
)

En validación cruzada, cada fold cumple temporalmente el papel de validación:

fold 1: validación | folds 2–5: entrenamiento
fold 2: validación | folds 1, 3–5: entrenamiento
...

Por eso no necesitamos un conjunto de validación fijo cuando utilizamos GridSearchCV.

Optimización de hiperparámetros

from sklearn.model_selection import GridSearchCV

param_grid = {
    "classifier__C": [0.01, 0.1, 1, 10, 100],
}

search = GridSearchCV(
    logistic_pipeline,
    param_grid=param_grid,
    scoring="roc_auc",
    cv=cv,
    n_jobs=-1,
)

search.fit(X_train, y_train)

El nombre classifier__C significa:

paso del pipeline __ hiperparámetro del objeto

Selección del campeón

Podemos comparar árbol, regresión logística y KNN, pero la selección debe hacerse con los resultados de validación cruzada:

champion_name = comparison.loc[0, "model"]
champion = searches[champion_name].best_estimator_

En este momento todavía no hemos usado test.

8. Notebook 5: evaluación final

Abrir test una sola vez

test_df = pd.read_csv("data/processed/test.csv")
X_test = test_df[contract["features"]]
y_test = test_df[contract["target"]]

y_pred = champion.predict(X_test)

Métricas

from sklearn.metrics import (
    accuracy_score,
    classification_report,
    ConfusionMatrixDisplay,
)

print("Accuracy:", accuracy_score(y_test, y_pred))
print(classification_report(y_test, y_pred))
ConfusionMatrixDisplay.from_predictions(y_test, y_pred)

La matriz de confusión muestra qué tipos de error comete el modelo. En un problema médico, confundir un caso maligno con benigno puede tener consecuencias diferentes a confundir un caso benigno con maligno. Por eso accuracy no siempre es suficiente.

Una distinción importante

Evaluar varios modelos en test y escoger el mejor convierte indirectamente test en un conjunto de validación.

La secuencia correcta es:

comparar con CV → elegir campeón → evaluar campeón en test

9. Notebook 6: inferencia y despliegue

Guardar el pipeline completo

import joblib

joblib.dump(champion, "artifacts/champion_model.joblib")

No guardamos solamente el clasificador. El artefacto debe contener también:

  • imputación;
  • escalamiento;
  • orden y selección de columnas;
  • modelo final.

Volver a cargar

model = joblib.load("artifacts/champion_model.joblib")
predictions = model.predict(new_data)

Validar el esquema

def validate_input(records, feature_columns):
    missing = sorted(set(feature_columns) - set(records.columns))

    if missing:
        raise ValueError(f"Faltan columnas: {missing}")

    return records[feature_columns]

La validación es importante porque el modelo puede recibir:

  • columnas faltantes;
  • columnas adicionales;
  • columnas desordenadas;
  • tipos incorrectos;
  • distribuciones diferentes a las observadas durante entrenamiento.

Predicción por lotes

def predict(records):
    X = validate_input(records, feature_columns)
    labels = model.predict(X)
    probabilities = model.predict_proba(X)

    return pd.DataFrame({
        "prediction": labels,
        "probability_class_0": probabilities[:, 0],
        "probability_class_1": probabilities[:, 1],
    })

Este núcleo puede utilizarse después desde una API, aplicación web o proceso batch.

11. Errores comunes

Explorar test

# Incorrecto
test_df.describe()

Aunque no entrenemos directamente con test, usarlo para tomar decisiones introduce información que no tendríamos sobre datos futuros.

Escalar antes del split o de la validación cruzada

# Incorrecto
X_scaled = scaler.fit_transform(X)
X_train, X_test = train_test_split(X_scaled)

El scaler aprendió usando también test.

Guardar solo el clasificador

# Insuficiente
joblib.dump(logistic_model, "model.joblib")

Si el modelo necesita escalamiento, la aplicación tendría que reconstruir manualmente el mismo procesamiento.

Escoger el modelo por test

# Incorrecto
best_model = max(models, key=lambda model: model.score(X_test, y_test))

La selección debe ocurrir con validación cruzada.

Depender del estado invisible del notebook

Una celda puede funcionar solo porque ejecutamos previamente otra celda fuera de orden. Cada notebook debe declarar sus entradas y cargar sus artefactos explícitamente.

12. ¿Por qué notebooks ahora y scripts después?

Los notebooks son adecuados para:

  • aprender;
  • explorar datos;
  • visualizar resultados;
  • documentar decisiones;
  • experimentar de forma interactiva.

Los scripts y módulos son mejores para:

  • ejecutar automáticamente;
  • probar funciones;
  • reutilizar código;
  • programar pipelines;
  • desplegar en producción.

La evolución natural es:

flowchart LR
    A[Notebook exploratorio] --> B[Funciones reutilizables]
    B --> C[Scripts de ejecución]
    C --> D[Pipeline automatizado]
    D --> E[Servicio de inferencia]

El notebook no desaparece: conserva la explicación y el análisis. El código estable se mueve a src/ y los comandos de ejecución a scripts/.

Ejemplo futuro:

project/
├── src/
│   ├── data.py
│   ├── features.py
│   ├── train.py
│   └── predict.py
├── scripts/
│   ├── prepare_data.py
│   ├── train_model.py
│   └── batch_predict.py
└── notebooks/
    ├── eda.ipynb
    └── model_analysis.ipynb

src/train.py contiene la lógica reutilizable. scripts/train_model.py recibe parámetros, llama esas funciones y permite ejecutar el entrenamiento desde consola.

    • crea train.csv, test.csv y el contrato.

  2. 02_training_challenge.ipynb

    • compara árbol, regresión logística y KNN;
    • optimiza hiperparámetros;
    • guarda el campeón.

  3. 03_evaluation_deployment_challenge.ipynb

La división obliga a que los estudiantes comuniquen las etapas mediante archivos y no mediante variables que existen únicamente en la memoria del notebook.

14. Ideas clave para recordar

  1. El objetivo no es entrenar un modelo aislado, sino construir un proceso reproducible.
  2. El EDA y las decisiones de diseño se hacen con entrenamiento.
  3. Las transformaciones aprendidas deben permanecer dentro del pipeline.
  4. La validación cruzada sirve para comparar y seleccionar.
  5. Test sirve para la evaluación final, no para tomar decisiones.
  6. El artefacto desplegable debe incluir procesamiento y modelo.
  7. Dividir notebooks hace explícitas las entradas, salidas y responsabilidades.
  8. Esta estructura es un puente entre experimentación y MLOps.
